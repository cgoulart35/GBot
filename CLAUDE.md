## Project

GBot is a Dockerized Python Discord bot (built on `nextcord`, not discord.py) backed by Google Firebase Realtime Database. It also exposes an in-process Quart HTTPS API for management/automation. Features are grouped into cogs: Agent, Config, GCoin, GTrade, Help, Hype, Music, Patreon, Presence, Storms, Who Dis. Halo features are deliberately discontinued but kept commented in-place (see "Halo" note below).

## Run / build

Bot only runs inside Docker. The Dockerfile generates self-signed TLS certs (`/GBot/server.{crt,key}`) at build time — the Quart API will not start without them, so you cannot meaningfully run `main.py` outside the container.

- Dev (runs the `gbot.dev01` identity; debugpy listening on host port 5677, API on 5003): `docker-compose -f docker-compose-dev.yml up -d --build`
- Prod (no debugger, API on 5004): `docker-compose -f docker-compose-prod.yml up -d --build`
- Both target stages share a `stage` base in `Dockerfile`; dev's entrypoint runs `main.py` under a **non-blocking** debugpy listener (attach whenever, or never — it dropped `--wait-for-client`, which used to make attaching a startup requirement and left the container hung without one), prod runs `main.py` directly (no debugpy, no debug port — hardened in Phase 6).
- `docker-compose-prod.yml` names the published image (`ghcr.io/cgoulart35/gbot:${IMAGE_TAG:-latest}`): with `--build` it builds that tag locally, plain `up -d` pulls from GHCR. Production deployment is image-based CD — CI's `publish` job ships an arm64 image on every code push to `develop`, and `scripts/deploy-watcher.sh` on the Pi redeploys via `scripts/deploy.sh` (see README §Deployment).

Before either works, populate the env file (Discord token, Firebase JSON, Patreon IDs, timeouts) and drop `Shared/serviceAccountKey.json` next to it. README §"Setup Guide" enumerates every env var.

**Two instances, one compose file each.** There are two Discord applications — `gbot.prod01` (`#6890`) and `gbot.dev01` (`#9690`) — differing only by `DISCORD_TOKEN` and sharing one Firebase project. **Prod runs on the Pi; dev runs only where it is being tested** (currently the Mac, via `/qa`), and is otherwise down. Each compose file names its own env file outright: `docker-compose-prod.yml` → `Shared/gbot.env`, `docker-compose-dev.yml` → `Shared/gbot.env.dev`. `scripts/qa.sh` just picks which file to bring up; it overrides nothing inside them. All `Shared/gbot.env*` files are gitignored except the tracked `.example`. The governing rule is **one token runs in exactly one place at a time** — two connections on one application double-fire every gateway event — so running prod locally means stopping it on the Pi first and putting it back after. Dev has nothing to stop or restore.

## Tests

`unittest.TestCase` suites run by **pytest** (the standardized runner — it collects them natively; `pytest.ini` keeps the archived Halo suites ignored, mirroring `test.py`'s `# DISCONTINUED` imports). Tests live in `GBotDiscord/test/<cog>/<cog>_test.py` and heavily mock `GBotFirebaseService` static methods. **Always run from the repo root** so the `GBotDiscord.src...` / `GBotDiscord.test...` package imports resolve.

The canonical way to run tests is `scripts/test.sh` — it builds the test image via `docker-compose-test.yml` (`stage` target: runtime deps only, no entrypoint), mounts the repo at `/GBot`, installs `requirements-dev.txt` ad hoc (pytest/coverage/pip-audit are dev-only, never in the runtime image), and runs `python -m pytest -q`; extra args pass through to pytest (`scripts/test.sh -k storm`, or a test path for one cog's suite). `scripts/test.sh audit` runs pip-audit over `requirements.txt` instead; `scripts/test.sh coverage` runs the suite under coverage and prints the 100%-gate report. No `Shared/gbot.env` or `serviceAccountKey.json` required because tests mock Firebase and Discord.

- Manual image build: `docker-compose -f docker-compose-test.yml build` (re-run only when `requirements.txt` changes; the wrapper does this every run).
- Manual all-suites run: `docker-compose -f docker-compose-test.yml run --rm --entrypoint sh gbot-test -c "pip install -r requirements-dev.txt -q && python -m pytest -q"`
- Single cog: `docker-compose -f docker-compose-test.yml run --rm gbot-test -m unittest GBotDiscord/test/<cog>/<cog>_test.py`
- Legacy entry point: `docker-compose -f docker-compose-test.yml run --rm gbot-test GBotDiscord/test/test.py` — still supported as the local/VS Code path; `sys.exit(0 if result.wasSuccessful() else 1)` keeps its exit code CI-safe. New test modules must be wired into both pytest discovery (automatic via `<x>_test.py` naming) and `test.py`'s suite list.
- Volume mount means host edits are picked up without rebuild. It also carries the host's `__pycache__`, which would let cached bytecode suppress compile-time diagnostics (`SyntaxWarning` etc.) that a fresh CI checkout still reports — `docker-compose-test.yml` sets `PYTHONPYCACHEPREFIX=/tmp/pycache` so in-image runs and CI report identically. Don't remove it.
- Local alternative: the VS Code "Python: Current File" launch config still works — it sets `PYTHONPATH=${cwd}` which is required.
- CI: `.github/workflows/ci.yml` runs the same pytest suite plus `pip-audit -r requirements.txt` on every PR and every push to `develop` — Python 3.13 straight on the runner, no Docker, no system packages (tests mock Firebase/Discord). Code pushes to `develop` additionally run the `publish` job (native-arm64 runner) that pushes `ghcr.io/cgoulart35/gbot:latest` + `:<short-sha>`; doc/CI/website-only pushes are skipped via the `changes` job. Dependabot is security-updates-only via repo settings; there is no version-update config.
- **Website:** `site/` is the Jekyll source of the public site, `https://gbot.stormerg.com/`. `.github/workflows/site.yml` checks its links on PRs and deploys it to GitHub Pages from `develop`. It's left out of the bot image by `.dockerignore`, and editing it publishes no image. `scripts/site.sh` previews it on port 4000 (`build` and `check` also work).
- **Drift guard:** `site_drift_test.py` compares `site/_data/commands.json`, `site/_data/features.json`, the README's command and feature tables, the version and the changelog with the real command tree, `FEATURE_EMOJIS` and `GBOT_VERSION`, which lives in `GBotDiscord/src/version.py` and ships in the image, so a release changes nothing on the Pi. So changing a command's name, aliases, arguments or description means updating that JSON and the README table in the same PR. The changelog lives in both the README and `site/_includes/changelog.md`, word for word.
- **Changelog feed:** `.github/workflows/changelog-feed.yml` posts one line per merged PR or direct push on `develop` to the `#gbot-changelog` Discord channel, hiding `docs:`, `ci:` and `test:`. Each post is a labelled title (New, Fixed, Updated, Changed) plus, in small subtext, the first `Changelog: <sentence>` line of the PR description or commit message, if there is one. Its logic is `.github/scripts/changelog-feed.sh`, which runs locally with `DRY_RUN=true`. A manual run with `message` posts exact text instead. It lives under `.github/` so that changing it publishes no image.
- **yt-dlp bumps:** `.github/workflows/yt-dlp-bump.yml` runs monthly (plus `workflow_dispatch` — fire it the moment music breaks), resolves the latest **stable** from PyPI (`.info.version`, which excludes the near-daily `.dev0` nightlies), rewrites the pin, verifies it by running the suite + `pip-audit` against it, and opens a PR carrying that verdict. Monthly rather than weekly because bumps are one-line and accrue no refactor debt — `2025.2.19` → `2026.7.4` skipped ~30 releases and touched no Python. The pin carries the `default,pin-deno` extras, so `yt-dlp-ejs` and `deno` follow each bump (C-15). Dependabot can't cover this: `allow: [dependency-name: yt-dlp]` would scope **security** updates to yt-dlp too, and omitting `allow` floods every pip pin.

## Architecture

### Composition
`GBotDiscord/src/main.py` is the entrypoint and does, in order: init logger and output capture (`logging_setup.py`) → `GBotPropertiesManager.startPropertyManager()` → `GBotFirebaseService.startFirebaseScheduler()` → `applyDavePrepareEpochPatch()` → instantiate the `commands.Bot` → `load_extension('<cog>.<cog>_cog')` for each feature → register error/completion event handlers → `GBotAPIService.registerAPI(client)` → `discordClient.run(...)`. The Quart app is started as a task on the bot's asyncio loop (`gbotClient.loop.create_task(serve(app, config, shutdown_trigger = ...))`), so the API shares the event loop with the Discord client. The trigger is deliberate: without one hypercorn takes SIGTERM from nextcord, and `docker stop` has to force-kill the bot.

`dave_patch.py` is the one place GBot patches a third-party library: nextcord never dispatches voice opcode 24 (`DAVE_PREPARE_EPOCH`), so the bot never rejoins the MLS group when a voice channel goes solo → group and its audio becomes undecryptable (ledger C-13). It has a defined removal condition — `dave_patch_test.py`'s canary test fails the day nextcord dispatches the opcode itself, and the module goes with it. Don't add unrelated library patches here; this one exists because the alternative was a dead feature.

### Per-feature layout
Each feature has its own package `GBotDiscord/src/<feature>/` containing:
- `<feature>_cog.py` — the `commands.Cog` subclass (commands, listeners, `tasks.loop` background loops, in-memory per-guild state).
- `<feature>_queries.py` — thin functions wrapping `GBotFirebaseService` calls; the schema is documented as a comment block at the top of each queries file (e.g., `gcoin_queries.py` describes `gcoin/<userId>/{balance,history,username}`).

Cross-feature talk happens via `client.get_cog('<Name>')` (e.g., `discord_resource.py` reaches into `Patreon` and `Presence`); the storm/whodis resources do the same with `Storms`.

### Dual-mode commands (slash + legacy prefix)
Each feature is **one command, twice**: a `@nextcord.slash_command(...)` and a `@commands.command(...)` with the same name, aliases and arguments (`/music [search]`, `.music [search...]`). Both delegate to a shared `commonX(self, context, ...)` coroutine that accepts either `nextcord.Interaction` or `Context`; keep that pattern, it's load-bearing for the `legacy_prefix_commands` toggle. With no fields a command opens its feature's card, where buttons do what subcommands used to, and optional fields give a fast path (`/music <search>`, `/storms 42 5`, `/gcoin @someone`, `/whodis user:<name>`). Don't add subcommands back: `command_tree_test.py` guards the shape, each prefix command's check count, and that text the bot sends names only real commands and options. A card's buttons call the same `commonX` engines, through `pagination.CardReply` when what the engine sends should become the card's notice rather than a new message. Anything private that a prefix command opens goes through `pagination.openPrivately`, which posts a 🔒 Open one-liner, because only an interaction can be answered privately. Right-click menus (`@nextcord.user_command` / `@nextcord.message_command`) carry the same slash checks; Discord allows five of each, and `site/_data/menus.json` and the README's menu table document them.

Decorator order matters and is mirrored from `predicates.py`. Predicates take a positional `isSlashCommand` boolean; pass `True` on the slash variant so the predicate uses `application_checks.check` instead of `commands.check`. Slash variants also pass `guild_ids = GBotPropertiesManager.SLASH_COMMAND_TEST_GUILDS` so the env var can scope registration during development (empty list = global).

Typical predicate stack (order matters because errors surface the *first* failing check):
- Slash: `isGuildOrUserSubscribed(True)` → `isMessageSentInGuild(True)` → feature-specific checks.
- Prefix: feature-specific checks → `isFeatureEnabledForServer('toggle_legacy_prefix_commands', False)` → `isMessageSentInGuild()` → `isGuildOrUserSubscribed()`.

### Persistence (Firebase RTDB)
All DB I/O goes through `GBotFirebaseService` (`firebase.py`) — never call `firebase_admin` directly. Those calls block, so they wait off the event loop through `await GBotFirebaseService.run(function, *args)`, a single-worker queue. Query functions stay synchronous, and a step needing several calls passes one function doing all of them. **Other commands can run during every one of those waits.** So a check followed by a write needs either one function for both, or a lock across both: `GTrade.tradeLock` for items and trades, and the Storms and Who Dis locks for games. The primitives are `get/set/push/update/remove`, each taking a list of child keys (`["servers", serverId, "prefix"]`); `get` returns a small adapter object exposing `.val()` (pyrebase's old contract, kept so query call sites never changed). The service account key (`Shared/serviceAccountKey.json`) is the database credential; `authenticate` verifies API basic-auth logins against the Identity Toolkit REST API using the `apiKey` from `FIREBASE_CONFIG_JSON`. Tests mock these as `MagicMock`/`AsyncMock` on the class.

Schema is implicit — there's no migration framework. Two patterns are used:
1. **Lazy upgrade per server**: `config_queries.upgradeServerValues` runs on `on_ready` for every server and back-fills new top-level fields with defaults. When you add a server-config flag, add a check here.
2. **One-shot patch via API**: heavier schema changes live in `quart_api/development_queries.py` and are triggered manually by POSTing `{"action":{"name":"runDatabasePatch","patch":"<id>"}}` to `/GBot/private/development/`. Wire the patch name into the `if patch == ...` chain in `development_resource.py`.

`leaderboards` is a denormalized aggregate table. It's updated from two places: balance changes inside `gcoin_queries.performTransaction`'s atomic write and event counters via cogs calling `leaderboards_queries.incrementUserNumValue`. Keep these decoupled from the GCoin transaction primitives — `processTransactionForLeaderboardRewards` is the only call site that reads transaction memo strings ("Storms", "Who Dis", "x10", etc.) to credit aggregate stats.

### Configuration & runtime mutation
`GBotPropertiesManager` (`properties.py`) is a class-level singleton holding env config. `startPropertyManager()` loads everything; `determineValue` is the **single coercion point** — it handles ints, splittable int lists and `LOG_LEVEL`, and both env strings *and* already-typed API payloads pass through it. Defaults are coerced too (an omitted int property must not land as its string default). A subset is **mutable at runtime** via the `setProperty` API action — see the `MUTABLE_PROPERTIES` allowlist; anything not on it (e.g., `DISCORD_TOKEN`, `API_PORT`) is intentionally immutable and `setProperty` returns `False`. A mutable property given an uncoercible value raises `PropertyValueInvalid`, which `development_resource` turns into a failure response. When adding a property: declare class attribute → load in `startPropertyManager` → optionally add to `INT_PROPERTIES`/`SPLITTABLE_INT_PROPERTIES` → optionally add to `MUTABLE_PROPERTIES`.

### Quart API
Routes are declared in `quart_api/api.py` and forward to `*Resource` classes that own `doc()` (returns the schema) and `post()`. All `/GBot/private/*` routes use HTTP basic auth verified against Firebase Auth (`GBotFirebaseService.authenticate`). `/GBot/public/leaderboard/` is unauthenticated. A resource's unexpected failure goes through `quart_api/errors.py`: 400 for a request that makes no sense, or logged and 500. Self-signed certs are baked into the image; `cors(app, allow_origin="*")` is intentional for the public leaderboard endpoint.

The `Development` resource is the operational lever for the deployed bot — `runDatabasePatch` applies a one-shot schema patch; `setProperty` mutates `GBotPropertiesManager`; `syncSubscribers` triggers `Patreon.patreon_validation()` immediately instead of waiting for the 24h task. Redeploys are **not** an API concern: they go through image-based CD (see README §Deployment).

### Patreon subscription gating
`isGuildOrUserSubscribed` is applied to nearly every user-facing command. Whether a server may use GBot is decided in one place, `access.py`: the ignore list, then the `patreon_members` Firebase table (populated by the `/patreon` slash command from inside the configured Patreon Discord server), then a free trial. A private-message command goes through if any server the user shares with GBot would. `ensureSubscribed`, `recheck` and `Patreon.patreon_validation` all ask `access`.

`PATREON_IGNORE_GUILDS` bypasses the check — `utils.getGuildsForPatreonToIgnore()` always appends `PATREON_GUILD_ID` to that list, so the Patreon coordination server itself is implicitly ignored. The API's `leaveGuild` also refuses ignored guilds unless the action sets `"optionalForce": true`.

**Trials:** a server GBot joins that is neither ignored nor subscribed, and has never had one, gets `TRIAL_DAYS` free (`trials/<serverId>`, kept after GBot leaves so re-adding it starts none). Servers GBot was already in when trials shipped have no record and get none. Once it ends, commands answer `AccessEnded` with a Patreon button, while presses on cards and games opened before (`recheck`, trade buttons) still work for `GRACE_DAYS`. Storms and Hype, which act on their own rather than on a command, ask `access.isActive` and stop then too, as the agent does. Then the 24h `patreon_validation` leaves, as it does any server that isn't subscribed, ignored or on a trial. `Patreon.trial_reminders` (hourly) tells admins at 2 days left, on the last day and at the end, recording each so none repeats. **Lapses** get the same grace: a patron who loses the role, or leaves the Patreon server, is marked `lapsed` rather than dropped, their server is refused like an ended trial (`access.LAPSED`) and told once, and the entry goes only after `GRACE_DAYS`, unless the role comes back or they run `/patreon` again. Both lengths are read live, so `setProperty` changes running trials and lapses.

### Per-guild in-memory state
`Storms`, `Music`, `WhoDis` keep state in instance dicts keyed by `str(guildId)`. The lifecycle is: `on_ready` builds state for every guild in `client.guilds` that doesn't have it yet, on every reconnect too, since a guild that added the bot while it was offline never gets a join event; `on_guild_join` initializes for new joins; `on_guild_remove` tears down. `Config` does the same for missing `servers/<id>` entries, and only ever fills a missing one. When adding new per-guild stateful behavior, wire all three listeners.

### User-facing output
`presentation.py` builds what users see: brand, error and warning embeds with a standard footer, and `sendReply`, which works with either an `Interaction` or a `Context` and handles ephemeral. `sendCommandError` is the central handler for every failed command. `sendError` is for refusals, and new output should go through this module. Buttons come from `pagination.py`: paged lists, `ListPicker` (a dropdown plus action buttons, a second row of them on row 3, and a confirm step for anything that can't be undone), `confirm` for a single yes or no, `Form` for typing, Discord's own member, channel and role pickers (`OwnedView.picker`), and `persistentButton` for a button on a long-lived message, whose `custom_id` (`music:skip`, `report:handled:<id>:<member>`) a cog's `on_interaction` listener answers, so it works after a restart. Every private card ends with ✖️ Close (`OwnedView.closeButton`), as paged lists always have. Every press checks permissions again with `predicates.recheck`, and a failing press is answered by `presentation.sendInteractionError`. Only whoever ran the command can press a card's buttons, except those meant for everyone: a Storm's, a trade's, the music card's (for people in GBot's voice channel) and a report card's (for admins). Nothing waits for a typed reply in the channel any more, so new interactions use these or a form (`nextcord.ui.Modal`) instead. Tests that build real lists call `isolation.restorePagination()` in `setUp`, because older suites replace parts of `pagination` and never put them back. Feature emoji live in `strings.FEATURE_EMOJIS`, and one-line confirmations lead with one. Errors stay plain and red, so a refusal is easy to spot. `ALLOWED_MENTIONS` is set on the Bot, so repeated user text can't ping `@everyone` or a role. After `deferIfSlash`, other commands can run, so moving money still needs the database rule under Persistence. Plain text is fine for one-line confirmations. `help/help_cog.py` owns `/help` and `.help`: the front door, with a button opening each feature's card for whoever may use it, and a dropdown for each feature's page. `help/guides.py` holds each feature's "How it works" text, which those pages show and the agent reads on request. Its numbers come from settings and the cogs' class constants, so they can't drift.

### The agent cog
`agent/` lets admins set up a Claude-powered agent in plain words. **Its safety doesn't depend on the model behaving, since anyone in a server can write to it.** It can only reply, react, stay silent and ask to save, change or forget a memory. `memoryAccess` decides who can save one: `admins`, or `everyone`, up to a per-member limit. It reads bot embeds and the preview cards of links (marked as a website's words), waiting a moment for a new link's preview to arrive, and with images on sees their pictures through Discord's copy. Key, model, limits and memory access apply to the whole server. A channel's mode, access, images and mentions override the server's. Its instructions and memories add to the server's and win if they disagree. Changing one is capped per message, checked in code (admins any, members only their own facts when `memoryAccess` is `everyone`), and the agent says what changed in its own reply, as it does when saving one. `/agent` follows the same rule: admins get its home card, and members only their memory card. `Agent.runTool` checks Discord roles in code before any tool runs, settings only change through `/agent`'s card, and replies ping nothing unless the `mentions` setting allows it: then only people in the messages it read and, at most, roles the sender could mention themselves, capped per reply and enforced in code, never `@everyone`. Don't give it a tool that can act on anything else without re-opening that design. Everything Claude-specific stays in `agent_client.py`, which uses the regular `anthropic` SDK rather than the Agent SDK, whose file and shell tools don't belong here. Servers on the ignore list use GBot's key, and the rest only ever use their own, stored encrypted with `AGENT_KEY_SECRET`. On GBot's key, only the bot application's owner can change limits and the model (`Agent.maySpend`), and `AGENT_SHARED_DAILY_TOKEN_LIMIT` caps those servers together. Keys are redacted from every log line by `logging_setup.redact`, because nextcord logs whole gateway events at DEBUG, and a subscription token is refused rather than stored. Whoever saved a memory is recorded from their role at the time: only an admin's can steer behaviour.

### Logging
`logging_setup.py` makes every line valid JSON, so any line can be pasted into a formatter: `JsonLineFormatter` uses `json.dumps`, nests a message that is itself a JSON object or list, and puts tracebacks in an `exception` field. `main.py` also redirects the process's stdout and stderr through `captureStream`, so subprocesses and library prints become JSON lines too (ffmpeg's errors arrive as `name: stderr`). Only output from before logging starts, or lost in a hard crash, stays plain. Don't `print()` anyway — use `self.logger` / `logging.getLogger()` so lines keep their level and source. Logs go to both `Logs/GBotDiscord.log` and stdout. yt-dlp's routine lines, API reads (including the public leaderboard's full response) and `nextcord.player` are deliberately quiet at INFO; API writes keep their full payload and response.

## Conventions worth knowing

- **What GBot asks Discord for** lives in `server_setup.py`: the gateway intents, the invite link's exact permissions (never Administrator) and `/config`'s ⚠️ Setup check. A feature needing a new intent or permission adds it there, with a test, and the README's setup step follows.
- Imports always use the full package path: `from GBotDiscord.src.<feature> import <queries>`. Relative imports break the test harness.
- Files use `#region IMPORTS` / `#endregion` banners; keep them when editing.
- Halo features (Halo Infinite API integration, two API resources, an entire cog) are kept in-tree but commented out with `# DISCONTINUED` markers throughout `main.py`, `api.py`, `test.py`, several cogs, and `config_queries.py`. Leave them alone — they're not dead code to clean up, they're an archived feature.
- Money values are `Decimal`, always rounded with `utils.roundDecimalPlaces(value, places)` (uses `ROUND_HALF_UP`) before display or persistence as a string.
- GCoin transactions go through `gcoin_queries.performTransaction` — a command that defers calls `validateTransaction` first, so its refusals stay private — it enforces the invariants in `exceptions.py` (`EnforceRealUsersError`, `EnforceSenderFundsError`, etc.). It runs on the database worker and writes everything in one atomic `GBotFirebaseService.updateMany`, so a failure can't leave money half moved, and `extraChanges` lets an item move in that same write. Never write a balance any other way. This is safe for one program at a time, including sharding inside it; several programs on one database need the distributed lock described in Workstream B first.

## Upstream issues we carry patches for

Third-party defects GBot works around in-tree. Each entry must name the upstream report, the workaround, and **how we find out it's fixed** — the point of this register is that the patch gets *deleted*, not inherited forever. **Append a row whenever a new workaround lands, and delete the row when the workaround goes.** Don't add a patch here without a removal condition.

| Upstream | Defect | Our workaround | Removal condition |
|---|---|---|---|

## Skills (`/commands`)

Repo skills live in `.claude/skills/<name>/SKILL.md` (tracked in git) and are invokable as `/<name>`; all are also auto-invokable (Claude loads one when a request matches its `description`). They wrap the deterministic `scripts/` wrappers or the documented compose commands with the right flags, safety rails, and verification — prefer them over hand-deriving commands; **`/implement-dev-changes`** composes them into a full dev-change flow:

- **`/test [pytest-args | coverage | audit]`** — run the suite / the 100%-coverage gate / pip-audit the ephemeral-container way (wraps `scripts/test.sh`; the `gbot-test` image never touches `:latest`, so runs are invisible to the Pi's deploy watcher).
- **`/qa [up [dev|prod]|logs|ps|down]`** — manual QA against a REAL token and REAL Firebase (wraps `scripts/qa.sh`): builds the working tree as `:qa` (watcher-invisible) and runs it. **Defaults to the `gbot.dev01` identity**, which runs nowhere else — so the Pi's live bot keeps serving users and no swap is needed. The invariant is *one token, one place*, not "prod must be down"; `up prod` is only for changes needing the production identity and does require stopping the Pi first. Human-gated via `QA_CONFIRM=yes`.
- **`/prod-up`** / **`/prod-down`** / **`/prod-logs [N]`** — start / stop / inspect the prod container (`GBot_prod`) from the published GHCR image. `/prod-logs` is read-only; on the Pi, container start/stop is maintainer-run.
- **`/implement-dev-changes`** — the end-to-end dev-flow **orchestrator**: explore → plan → branch → implement (+tests) → `/test` (+ `coverage` when `GBotDiscord/src` changed) → optional `/qa` → commit → push → PR → review loop → pre-deploy checks → **merge (only on explicit OK)** → verify publish + Pi deploy. Pauses at every human gate; never merges/pushes/deploys unprompted.

## PR auto-review & accepted trade-offs

- **PR review (CI):** `.github/workflows/claude-review.yml` runs Claude (`anthropics/claude-code-action@v1`) on every non-draft PR (drafts get reviewed once marked ready), posting inline findings and a short summary comment; authed by the `CLAUDE_CODE_OAUTH_TOKEN` repo secret (a Claude subscription token, not API billing). Comments only — never approves or blocks. The action's **backend** validates the workflow against the **default branch** (`develop`): on any PR whose `claude-review.yml` differs from — or doesn't yet exist on — `develop`, the review job **skips gracefully** (green check + a "Skipping action due to workflow validation" warning; not a GitHub-side rule, and older action versions hard-failed with `401 Workflow validation failed` instead). So merge workflow changes on their own first — reviews only run once the file is on `develop`.
- **Review scope — accepted trade-offs (the auto-reviewer must NOT re-flag these):** Halo features commented in place with `# DISCONTINUED` markers (archived, not dead code); self-signed TLS certs baked into the image for the Quart API; `cors(app, allow_origin="*")` on the public leaderboard; the dual slash/prefix command duplication (load-bearing for `.config toggle legacy_prefix_commands`); the implicit RTDB schema (lazy `upgradeServerValues` + one-shot API patches, no migration framework); camelCase Python names; mutable GitHub Action version tags (`@vN` rather than SHA-pinned — so upstream fixes are picked up automatically); the review job skipping itself on workflow-editing PRs (the workflow-validation guard — see above); and the yt-dlp bump PRs being authored by the maintainer rather than a bot — `yt-dlp-bump.yml` pushes and opens them with `AUTOMATION_PR_TOKEN`, a fine-grained token scoped to this repo with no expiry, because GitHub held the CI and review runs of `GITHUB_TOKEN` PRs for manual approval. These are settled; a review that raises them is noise, not a finding. **Append a line here whenever a future review flags something we decide to accept** — this list is how the reviewer "learns" what to ignore (the prompt in `claude-review.yml` points at it).
